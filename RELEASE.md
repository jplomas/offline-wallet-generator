# Releasing

The hosted and downloadable releases are independent:

- Netlify runs `npm ci && npm run build:verified` and publishes `dist/` to
  <https://offline-wallet-generator.theqrl.org>.
- A signed `v*` tag builds `dist-offline/index.html`, verifies it is
  self-contained, proves in a browser that it makes no network requests, and
  publishes the HTML with its SHA-256 and a signed build-provenance
  attestation on GitHub Releases.

## The maintainer key allowlist

The release workflow verifies the tag signature against a committed allowlist.
A GitHub-hosted runner starts with an empty keyring, so verification cannot
succeed without one; the workflow fails closed if neither file below has at
least one real entry. A file containing only comments does not count.

`.github/allowed-signers` — SSH, one line per key:

```
<principal> [namespaces="git"] <key-type> <base64-key>
```

**Multiple keys per maintainer are supported** — repeat the principal on as
many lines as needed (laptop, hardware key, backup). Any listed key verifies.
`valid-before="YYYYMMDD"` retires a key without invalidating tags it already
signed, because git evaluates the window against the tag's own timestamp.

Alternatively `.github/maintainer-keys.asc` — ASCII-armoured PGP public keys,
from `gpg --armor --export <key-id>`. The workflow tries PGP first and accepts
either.

### What this proves, and what it does not

`git verify-tag` runs `ssh-keygen -Y find-principals`: it asks whether the
signing key is listed, **not** whether that key belongs to whoever made the
tag. A listed key verifies regardless of the tagger's email, and the principal
field is a human-readable label rather than an identity binding. The property
is *"signed by a key on the allowlist"*, which is what a release gate needs —
it is simply not more than that.

**Any script touching this must gate on git's exit code.** `git verify-tag`
prints `Good "git" signature …` even for an unknown key and only then adds
`No principal matched.` on the next line, so matching on output would accept
an attacker's key.

### Adding a key

1. Get the maintainer's SSH **signing** public key. This is often not their
   GitHub authentication key from `https://github.com/<user>.keys`, and users
   of 1Password or Secretive sign with a key held in an agent — ask, do not
   infer.
2. Confirm the fingerprint (`ssh-keygen -lf <keyfile>`) **out of band**, over a
   channel that is not GitHub. Pulling a key from a URL and trusting it because
   the URL looked right is the whole attack.
3. Add the line, then have them prove it works before it is needed:

```bash
git tag -s v0.0.0-signing-test -m "signing test" && git -c gpg.format=ssh -c gpg.ssh.allowedSignersFile=.github/allowed-signers verify-tag v0.0.0-signing-test && git tag -d v0.0.0-signing-test
```

Publish the fingerprints somewhere users can obtain them independently of this
repository — an allowlist whose only source is the repo it protects proves
nothing against someone who can write to that repo. These keys are the root of
trust for every release.

## Cut an offline release

1. Bump and commit the version: `npm version <version> --no-git-tag-version`.
2. Merge and confirm the Netlify deployment first.
3. Sign the deployed commit: `git tag -s v<version> -m "QRL Offline Wallet <version>"`.
4. Verify it locally: `git verify-tag v<version>`.
5. Push it: `git push origin v<version>`.

The release workflow rejects a tag that is lightweight, that is not signed by a
key in the allowlist, that does not match `vMAJOR.MINOR.PATCH`, or whose
version differs from `package.json`.

## How users verify a download

Three checks of increasing strength. The first two are cheap; the third is
what actually establishes authenticity.

### 1. Checksum — detects a corrupted download

```bash
sha256sum -c qrl-offline-wallet-<version>.html.sha256
```

This is generated by the same job that builds the file, so it proves the
download arrived intact and **nothing about who built it**. Do not present it
as an authenticity check.

### 2. Build provenance — detects a file that did not come from this pipeline

```bash
gh attestation verify qrl-offline-wallet-<version>.html --repo theQRL/offline-wallet-generator
```

The attestation is signed via OIDC during the release run and binds the
artefact digest to this repository, this workflow, and the commit it was built
from. This is the check most users should run.

### 3. Rebuild and compare — detects anything at all

```bash
git clone https://github.com/theQRL/offline-wallet-generator.git
cd offline-wallet-generator
git checkout v<version>
nvm use            # or install the Node version in .nvmrc
npm ci && npm run build:offline
sha256sum dist-offline/index.html
```

The digest must equal the one in the published `.sha256`.

**A `git clone` and tag checkout are required.** The build embeds a build
identifier derived from `git rev-parse HEAD`, so building from the "Source
code (tar.gz)" asset attached to the release — which contains no `.git`
directory — stamps `<version>+unknown` and produces a **different digest on a
genuine artefact**. If you must build from a tarball, set `COMMIT_REF` to the
full tagged commit SHA:

```bash
COMMIT_REF=<40-char commit sha> npm run build:offline
```

**Use the Node version in `.nvmrc`.** Node 22 and 24 currently produce
identical output, but that is verified rather than guaranteed.

**Rebuild verification works on Linux, macOS and Windows.** Measured on
2026-08-03: all three produced a byte-identical artefact from the same commit,
so a digest mismatch on any of them is meaningful and should be treated as a
real signal rather than a platform quirk.

Two things make that hold, and both are load-bearing:

- `.gitattributes` pins the working tree to LF. Windows otherwise checks out
  text files as CRLF and those carriage returns reach the artefact — it
  differed by exactly 70 bytes before this was added.
- The CSS pipeline uses platform-specific native binaries (`lightningcss`,
  `@tailwindcss/oxide`), which was the obvious suspect for divergence and
  turned out not to be one. If either is upgraded, re-check across platforms
  rather than assuming.

CI builds the artefact twice on every push and fails on a digest mismatch, so
the single-platform half of this is continuously tested. The cross-platform
half was a one-off measurement — worth repeating after a toolchain change.

CI runs the offline build twice on every push and fails if the two digests
differ, so the instruction above is continuously tested rather than assumed.
